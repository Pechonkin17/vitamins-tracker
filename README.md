# Vitamins Tracker

Мінімальна структура монорепо вебзастосунку для обліку харчування, калорій та вітамінів.
На цьому етапі репозиторій містить лише каталоги, без коду, залежностей і конфігурації запуску.

## Структура

```text
backend/
  app/
    api/               # HTTP-маршрути, API-схеми та DI
    core/              # конфігурація й наскрізні механізми
    db/                # підключення та сесії БД
    modules/
      users/           # користувач
      food_log/        # записи їжі та води
      nutrition/       # нутрієнти й підсумки
    integrations/      # зовнішні сервіси, майбутній LangGraph
  migrations/          # майбутні міграції БД
  tests/
frontend/
  src/
    app/               # маршрути та компонування Next.js
    features/          # функціональні модулі
    shared/            # спільні UI-компоненти та утиліти
  public/              # статичні ресурси
docs/                  # документи 000–011, залишені без змін
```

Порожні каталоги зберігаються через `.gitkeep`.

## Принципи

KISS і YAGNI: додаємо реалізацію та додаткові шари під конкретний сценарій.
DRY: виносимо спільний код після появи реального повторення.
SOLID: розділяємо відповідальність і передаємо залежності явно;
не створюємо абстрактних базових класів без потреби.

У бекенді HTTP-рівень прийматиме запити й викликатиме сервіси модулів.
Сервіси відповідатимуть за сценарії та транзакції, репозиторії — за запити до БД.
Pydantic-схеми відокремлюватимуться від ORM-моделей. Конкретні файли цих шарів
з’являться разом із функціями, без порожніх реалізацій наперед.

FastAPI, Poetry, async SQLAlchemy, PostgreSQL, Next.js, Docker та CI
налаштовуватимемо покроково в наступних ітераціях.
